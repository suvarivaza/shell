# Server Setup

Документация для интерактивного скрипта [`server_setup.sh`](server_setup.sh).

## Назначение

`server_setup.sh` предназначен для первичной настройки и последующей проверки Linux-сервера. Скрипт объединяет операции с SSH, Fail2Ban, Nginx, пользователями, сетью, `iptables`, базовой установкой Docker и зашифрованными внешними резервными копиями Restic.

Название `Server Setup` оставлено намеренно: безопасность является основной частью скрипта, но он также содержит общую диагностику и административные операции.

## Поддерживаемое окружение

Скрипт рассчитан прежде всего на Debian и Ubuntu с:

- `systemd`;
- OpenSSH Server;
- `sudo`;
- `iptables` и `ip6tables`;
- пакетным менеджером APT;
- Nginx и Fail2Ban для соответствующих разделов меню.

Часть диагностических функций будет работать и без Nginx или Fail2Ban. Установка Fail2Ban и `iptables-persistent` использует APT, поэтому на системах другого семейства эти операции выполнять нельзя.

## Запуск

```bash
chmod +x server_setup.sh
./server_setup.sh
```

Запускать весь скрипт от `root` необязательно: команды, которым нужны повышенные права, используют `sudo`.

Не рекомендуется запускать скрипт напрямую из непроверенного удалённого URL. Сначала сохраните файл локально, проверьте его содержимое и только после этого запускайте.

## Резервные копии

Перед изменением критичных конфигураций скрипт сохраняет резервные копии в:

```text
/root/server-setup-backups
```

В этот каталог попадают:

- предыдущая конфигурация SSH, созданная скриптом;
- предыдущая конфигурация Fail2Ban, созданная скриптом;
- полные активные правила IPv4 и IPv6 перед изменением `iptables`;
- содержимое `ipset`, если утилита установлена.

Резервные копии не удаляются автоматически.

## Предварительный просмотр команд

Перед подтверждением каждой операции, изменяющей сервер, скрипт показывает итоговые команды и рассчитанные аргументы в shell-формате. Специальные символы экранируются через формат `%q`, поэтому в выводе видно, какое значение будет передано отдельным аргументом.

Для многошаговых операций выводится общий план команд, после которого задаётся один вопрос о применении всего плана. Дополнительно показываются пути и ключевые значения управляемых конфигурационных файлов. После подтверждения каждая фактически запускаемая изменяющая команда повторно печатается непосредственно перед выполнением — уже с реальными временными путями и параметрами. Диагностические проверки не требуют подтверждения, поскольку не изменяют сервер.

Внутренние проверки, создание резервных копий и команды автоматического отката не включаются в подтверждаемый план: они обеспечивают безопасное выполнение уже подтверждённой операции.

## Рекомендуемый порядок первичной настройки

1. Запустить пункт **«Аудит безопасности без изменений»** и сохранить результат.
2. Проверить, что вход по SSH-ключу действительно работает во второй терминальной сессии.
3. Отключить парольный вход через раздел **SSH**.
4. Установить и настроить Fail2Ban.
5. Ограничить доступ к ISPmanager разрешёнными IP-адресами.
6. Проверить сохранение правил `iptables` после перезагрузки.
7. Включить автоматические обновления безопасности.
8. Проверить открытые порты и убедиться, что лишние службы не слушают внешний интерфейс.
9. Выполнить проверку файловой системы.
10. Повторно выполнить аудит и сохранить итоговый отчёт.
11. Настроить отдельный внешний репозиторий Restic, выполнить первый backup и контрольное восстановление.

Текущую SSH-сессию нельзя закрывать, пока вход по ключу и доступ к панели не проверены из отдельного соединения.

## Главное меню

### 1. Система

Раздел содержит диагностические операции:

- **Информация о системе** — показывает `/etc/os-release` и `hostnamectl`.
- **Все сервисы** — выводит загруженные службы `systemd` без интерактивного pager.
- **Системные логи** — запускает просмотр `/var/log/syslog` в реальном времени. Для выхода используется `Ctrl+C`.

Раздел не изменяет конфигурацию сервера.

### 2. SSH

#### Проверить SSH-настройки

Выводит эффективную конфигурацию через `sshd -T`, а не только строки из отдельных файлов. Проверяются:

- `PasswordAuthentication`;
- `PubkeyAuthentication`;
- `KbdInteractiveAuthentication`;
- `MaxAuthTries`;
- `PermitRootLogin`.

#### Заблокировать доступ по паролю

Операция:

1. Проверяет наличие непустого `authorized_keys` у текущего пользователя или `root`.
2. Предупреждает о риске потери доступа и просит проверить вход по ключу во второй SSH-сессии.
3. Требует обычное подтверждение и точный ввод слова `ПРОВЕРЕН`.
4. Создаёт резервную копию существующего файла.
5. Записывает `/etc/ssh/sshd_config.d/99-custom.conf`.
6. Отключает парольную и интерактивную авторизацию.
7. Ограничивает число попыток авторизации значением `5`.
8. Проверяет конфигурацию командой `sshd -t`.
9. Перечитывает конфигурацию SSH без остановки службы.
10. Автоматически возвращает предыдущий файл при ошибке проверки или перезагрузки.

После выполнения необходимо открыть второе SSH-соединение и проверить вход по ключу до закрытия текущей сессии.

#### Проверить отключение пароля

Проверяет, что эффективная конфигурация содержит:

```text
passwordauthentication no
```

Функция не пытается выполнить реальную авторизацию и не запрашивает пароль.

#### Найти настройки в SSH-конфигах

Показывает значимые директивы из основного файла и каталога `sshd_config.d`. Используется для поиска конфликтующих или переопределяющих настроек.

#### Настроить root-доступ

Предлагает два режима:

- разрешить `root` только по SSH-ключу — `PermitRootLogin prohibit-password`;
- полностью запретить вход `root` — `PermitRootLogin no`.

Полный запрет доступен только при наличии другого пользователя в группе `sudo` с непустым `authorized_keys`. Перед применением создаётся резервная копия, выполняется `sshd -t`, а при ошибке конфигурация откатывается.

Перед полным запретом `root` необходимо подтвердить точным словом `ПРОВЕРЕН`, что вход альтернативным администратором с `sudo` уже успешно проверен в отдельной SSH-сессии.

### 3. Fail2Ban

#### Установить Fail2Ban

После явного подтверждения обновляет индекс APT, устанавливает пакет `fail2ban`, включает службу в автозагрузку и запускает её.

После установки выводятся содержимое конфигурации ISPmanager, конфигурации Server Setup, результат проверки и список активных jail.

#### Показать статус

Доступны общий статус службы и состояние конкретного jail.

#### Настроить Fail2Ban

Создаёт управляемый файл:

```text
/etc/fail2ban/jail.d/99-server-setup.conf
```

ISPmanager использует отдельный файл:

```text
/etc/fail2ban/jail.local
```

Server Setup не изменяет `jail.local`. После установки и после применения конфигурации скрипт выводит оба файла с заголовками, выполняет `fail2ban-client -t` и показывает общий статус с активными jail. Эти сведения также доступны отдельным пунктом меню Fail2Ban.

Перед заменой управляемого файла и перезапуском службы запрашивается явное подтверждение.

Всегда включает jail `sshd`. Фильтры `nginx-botsearch`, `nginx-noscript` и `exim` включаются только тогда, когда соответствующий фильтр установлен и существует необходимый журнал.

Перед применением выполняется `fail2ban-client -t`. При ошибке конфигурация откатывается. После перезапуска дополнительно проверяется активность службы.

Настройки по умолчанию:

- период наблюдения — 10 минут;
- блокировка — 1 час;
- допустимое число неудачных попыток — 5;
- локальные адреса исключены из блокировки.

#### Смотреть журнал

Запускает `tail -f /var/log/fail2ban.log`. Для выхода используется `Ctrl+C`.

### 4. Пользователи

Раздел позволяет:

- создать обычного системного пользователя через `adduser`;
- создать администратора и после явного подтверждения добавить его в группу `sudo`;
- установить пользователю публичный SSH-ключ.

Создание пользователя, выдача прав `sudo` и установка SSH-ключа выполняются только после отдельных явных подтверждений.

Перед запуском проверяется формат имени и отсутствие существующей учётной записи. Функция не добавляет пользователя в группу `sudo` автоматически.

Публичный ключ проверяется по формату, записывается в `authorized_keys`, после чего устанавливаются права `700` для `.ssh` и `600` для `authorized_keys`.

### 5. Nginx

#### Показать статус

Выводит состояние службы без интерактивного pager.

#### Проверить и перечитать конфигурацию

Сначала выполняет:

```bash
sudo nginx -t
```

Только после успешной проверки выполняется `systemctl reload nginx`. Перезапуск процесса с разрывом соединений не используется.

После проверки скрипт отдельно запрашивает подтверждение перед перечитыванием конфигурации Nginx.

#### Блокировка нежелательных ботов

Раздел позволяет показать, установить, обновить или удалить управляемый файл:

```text
/etc/nginx/vhosts-includes/bad_robot.conf
```

Правило проверяет заголовок `User-Agent` без учёта регистра и отвечает кодом `444` для перечисленных роботов и инструментов. Используется один безопасный для этого сценария блок `if` с непосредственным `return`, без промежуточной переменной `set`.

Перед установкой скрипт:

1. Показывает полное содержимое будущего файла и команды.
2. Предупреждает о широких шаблонах `python`, `pycurl` и `urllib`.
3. Запрашивает явное подтверждение.
4. Создаёт резервную копию существующего файла.
5. Проверяет конфигурацию через `nginx -t`.
6. Проверяет через `nginx -T`, что файл действительно подключён активной конфигурацией ISPmanager.
7. Перечитывает Nginx без остановки службы.
8. Восстанавливает предыдущий файл при ошибке проверки или reload.

Фильтрация по `User-Agent` является только дополнительным снижением нежелательного трафика: заголовок легко изменить, а слишком общие шаблоны способны заблокировать легитимный мониторинг, API-клиенты или интеграции. Правило не заменяет ограничение портов, Fail2Ban, WAF и обновление программного обеспечения.

### 6. Сеть

Раздел содержит две разные проверки.

#### Все слушающие порты

Показывает все слушающие TCP- и UDP-сокеты, процессы и PID через:

```bash
sudo ss -lntup
```

Сюда входят как публичные сокеты, так и службы, доступные только через
`127.0.0.1` или `::1`.

#### Потенциально открытые наружу порты

Показывает сокеты, которые не привязаны к loopback-адресам `127.0.0.1` и
`::1`. В этот список попадают службы, слушающие `0.0.0.0`, `[::]`, публичный
или частный сетевой адрес сервера.

Это список потенциально публичных портов. Он не доказывает, что соединение
действительно пройдёт из интернета: доступ может быть закрыт `iptables`,
фаерволом хостинга, NAT или маршрутизацией.

Точная проверка выполняется с другого сервера или компьютера:

```bash
nmap -Pn -sS -sV <публичный-IP>
sudo nmap -Pn -sU --top-ports 100 <публичный-IP>
```

TCP- и UDP-сканирование необходимо выполнять раздельно. UDP-проверка обычно
занимает значительно больше времени.

Обе функции раздела не изменяют сетевые настройки.

### 7. Фаервол iptables

#### Список правил

Показывает активные правила IPv4 с номерами строк.

#### Ограничить доступ к ISPmanager

Настраивает доступ к TCP-порту `1500`:

- создаёт управляемую IPv4-цепочку `ISPMGR_ACCESS`;
- разрешает указанные IPv4-адреса;
- отклоняет остальные IPv4-подключения к порту `1500`;
- создаёт цепочку `ISPMGR6_ACCESS` и закрывает порт по IPv6;
- сохраняет правила через `netfilter-persistent`;
- проверяет сохранённые правила командами `iptables-restore --test` и `ip6tables-restore --test`.

Перед любыми изменениями создаётся полная резервная копия активного фаервола. При ошибке изменения откатываются.

Если скрипт запущен по SSH, IP текущего подключения предлагается как значение по умолчанию. Это подсказка, а не гарантия: перед подтверждением адрес необходимо проверить вручную.

#### Показать доступ к ISPmanager

Показывает:

- IPv4 allowlist управляемой цепочки;
- прямые правила `INPUT` для порта `1500`;
- состояние IPv6-цепочки.

#### Добавить разрешённый IP

Добавляет IPv4-адрес перед завершающим правилом `DROP`, сохраняет конфигурацию и откатывает изменение при ошибке.

#### Удалить разрешённый IP

Удаляет адрес из управляемой цепочки и из поддерживаемого старого прямого правила. Скрипт запрещает удалять последний IPv4-адрес из allowlist.

#### Проверить сохранение правил

Показывает состояние `netfilter-persistent`, наличие файлов правил и проверяет возможность их восстановления без фактической перезагрузки фаервола.

### 8. Аудит безопасности без изменений

Собирает диагностический отчёт:

- версию ОС и ядра;
- эффективные настройки SSH;
- состояние SSH, Nginx, Docker, Fail2Ban, `netfilter-persistent` и FTP-сервера;
- все слушающие TCP- и UDP-порты;
- потенциально публичные порты без loopback-сокетов;
- пользователей с UID `0`;
- пользователей с интерактивной оболочкой;
- участников группы `sudo`;
- отпечатки установленных SSH-ключей;
- состояние Fail2Ban;
- активные IPv4- и IPv6-цепочки `INPUT`;
- состояние сохранения фаервола;
- состояние автоматических обновлений;
- доступные обновления пакетов.

Этот пункт не изменяет систему.

### 9. Автоматические обновления безопасности

Раздел устанавливает `unattended-upgrades`, включает таймеры APT и создаёт два управляемых файла:

```text
/etc/apt/apt.conf.d/20auto-upgrades
/etc/apt/apt.conf.d/52-server-setup-security-updates
```

Установка пакета, запись конфигурации и включение таймеров начинаются только после явного подтверждения.

Существующие файлы резервируются. Список источников очищается и ограничивается репозиторием с кодовым именем `*-security`. Автоматическая перезагрузка сервера отключена.

Пакеты из сторонних репозиториев, включая альтернативные сборки PHP ISPmanager, этим правилом автоматически не обновляются. Их необходимо контролировать и обновлять отдельно.

Перед завершением выполняется проверочный запуск `unattended-upgrade --dry-run`. В меню также доступны состояние таймеров, эффективная конфигурация APT и журнал обновлений.

### 10. Инвентаризация и отключение служб

Показывает состояние значимых служб и список слушающих портов. Проверяются веб-серверы, Docker, FTP, Telnet, базы данных, Redis, почтовые службы, Fail2Ban и фаервол.

Отключение разрешено только для ограниченного списка потенциально ненужных служб. Необходимо повторно ввести точное имя службы. Скрипт отдельно предупреждает, что остановка базы данных или почтового сервиса может нарушить работу приложений.

Службы SSH, Nginx, Apache, Fail2Ban и фаервол через эту функцию отключить нельзя.

Для ProFTPD предусмотрено отдельное понятное действие. Перед выполнением
скрипт показывает команду и требует точного ввода имени `proftpd`:

```bash
sudo systemctl disable --now proftpd
```

Команда немедленно останавливает FTP-сервер и исключает его из автозагрузки.
После выполнения скрипт проверяет состояние службы и наличие процессов на
стандартных FTP-портах `20` и `21`. SFTP работает через SSH и этим действием
не отключается. Пакет ProFTPD не удаляется; при необходимости службу можно
вернуть командой `sudo systemctl enable --now proftpd`.

Для сервера, который не принимает и не отправляет почту, предусмотрено
отдельное отключение почтового стека. Скрипт ищет только заранее ограниченный
список известных служб:

- Exim или Postfix;
- Dovecot;
- OpenDKIM;
- Rspamd или SpamAssassin;
- ClamAV.

Перед изменением выводятся найденные службы и итоговая команда
`systemctl disable --now`. Для продолжения необходимо точно ввести фразу
`ОТКЛЮЧИТЬ ПОЧТУ`.

Это действие нельзя выполнять только на основании отсутствия почтовых ящиков.
Сайт может использовать локальный Exim/Postfix для Joomla/PHP `mail()`, а cron,
Logwatch и другие системные службы — для административных уведомлений. Почтовый
стек следует отключать, только если приложения используют внешний SMTP либо
отправка почты на сервере вообще не нужна.

После отключения проверяются состояния найденных служб и стандартные порты:

```text
SMTP:       25, 465, 587
POP3:       110, 995
IMAP:       143, 993
```

Отключение служб не удаляет пакеты и конфигурацию. Скрипт показывает обратную
команду `systemctl enable --now` со списком фактически найденных служб.

### 11. Проверка файловой системы

Read-only проверка ищет:

- файлы и каталоги с правами записи для всех внутри `/var/www`;
- `.env`, `configuration.php`, `wp-config.php`, приватные ключи и сертификаты в каталогах сайтов;
- приватные SSH-файлы с доступом для группы или остальных пользователей;
- каталоги сайтов, принадлежащие `www-data` и доступные ему для записи.

Результат требует ручной оценки: каталоги загрузок, кеша и журналов могут законно быть доступны веб-серверу для записи.

### 12. Итоговый отчёт

Запускает общий read-only аудит и сохраняет его результат в закрытом системном каталоге:

```text
/root/server-security-reports/server-security-report-YYYYMMDD-HHMMSS.txt
```

Каталог создаётся с правами `700`, а отчёты — с правами `600` и владельцем
`root:root`. Путь не зависит от текущего каталога запуска, поэтому отчёт не
попадёт в DocumentRoot сайта. Для просмотра нужен `sudo`, например:

```bash
sudo less /root/server-security-reports/server-security-report-YYYYMMDD-HHMMSS.txt
```

Отчёт удобно сохранить перед настройкой, повторить после неё и сравнить результаты.

### 13. Docker

Раздел предназначен для типовой пакетной установки Docker на Debian или Ubuntu и содержит четыре операции:

- проверка версий Docker и Docker Compose, а также состояния `docker.service`;
- установка или обновление пакетов `docker.io` и `docker-compose-v2`;
- точечное обновление уже установленных пакетов через `apt-get install --only-upgrade`;
- добавление существующего пользователя в группы `docker` и, по отдельному выбору, `sudo`.

После установки выполняется `systemctl enable --now docker`: служба запускается и добавляется в автозагрузку. Отдельный принудительный `systemctl restart docker` не выполняется, поскольку он может прервать работающие контейнеры.

Обычная установка через `apt-get install` также обновляет уже установленные пакеты до доступной в подключённых репозиториях версии. Пункт точечного обновления оставлен как отдельная явно названная операция и не обновляет остальные пакеты системы.

Перед изменением групп скрипт предупреждает, что членство в группе `docker` фактически предоставляет привилегии уровня `root`. После выбора групп выводятся точные команды, а для окончательного подтверждения необходимо повторно ввести имя пользователя. Изменение групп начинает действовать только после нового входа пользователя в систему.

Скрипт использует пакеты из системных репозиториев и не подключает официальный репозиторий Docker Inc. Версия Docker поэтому определяется репозиториями установленной операционной системы.

### 14. Logwatch

Logwatch формирует читаемые сводки по системным журналам, для которых в пакете
установлены соответствующие анализаторы. Он не является системой мониторинга в
реальном времени, не блокирует атаки и не заменяет Fail2Ban, фаервол или
проверку состояния служб.

Раздел содержит следующие операции:

- показать версию, локальную конфигурацию и найденные задания автоматического запуска;
- установить пакет `logwatch` через системный репозиторий;
- сформировать в консоли отчёт по всем анализаторам за вчера;
- выбрать несколько анализаторов и получить отчёт за сегодня или вчера;
- показать реальные названия установленных анализаторов;
- настроить ежедневный почтовый отчёт.

Общий ручной отчёт выполняется с явно заданным выводом в консоль:

```bash
sudo logwatch --output stdout --format text --range yesterday --detail Med --service All
```

В выборочном отчёте каждый анализатор передаётся отдельным параметром
`--service`. Перед запуском скрипт проверяет его наличие в каталоге:

```text
/usr/share/logwatch/scripts/services
```

Значения `Low`, `Med` и `High` задают степень детализации отчёта. `Med` не
означает вывод только ошибок.

Настройка ежедневной почты является отдельной операцией. Скрипт запрашивает
адреса получателя и отправителя, показывает итоговые параметры, требует
подтверждение и создаёт резервную копию существующего файла:

```text
/etc/logwatch/conf/logwatch.conf
```

По умолчанию настраивается отчёт за вчера со средней детализацией по всем
установленным анализаторам. Фактическая отправка зависит от правильно
работающего почтового сервера. После настройки необходимо вручную проверить
доставку тестового отчёта. Само наличие Logwatch не подтверждает, что письмо
было принято внешним почтовым сервером.

### 15. GoAccess

GoAccess предназначен для ручного анализа журналов доступа Nginx или Apache.
Он помогает увидеть посещаемые страницы, источники трафика, HTTP-статусы,
клиентов и другие данные, уже записанные веб-сервером в `access.log`.

Раздел содержит следующие операции:

- показать установленную версию GoAccess;
- найти журналы доступа в типовых каталогах Nginx, Apache и ISPmanager;
- установить пакет `goaccess` из системного репозитория;
- запустить интерактивный анализ выбранного журнала.

Перед анализом необходимо указать абсолютный путь к существующему читаемому
файлу. Итоговая команда показывается перед запуском:

```bash
sudo goaccess /абсолютный/путь/access.log --log-format=COMBINED
```

Скрипт использует встроенный формат `COMBINED`, соответствующий стандартному
combined access log Nginx и Apache. Благодаря этому системный файл
`/etc/goaccess/goaccess.conf` не изменяется и не возникает конфликтов при
обновлении пакета.

Если конкретный виртуальный хост использует нестандартный `log_format`, его
необходимо сначала сопоставить с фактической конфигурацией Nginx или Apache.
Запуск с неверным форматом приведёт к ошибкам разбора либо некорректной
статистике, но не изменит исходный журнал.

### 16. Резервное копирование Restic

Раздел настраивает зашифрованные инкрементальные резервные копии на Hetzner
Storage Box через SFTP. Каждый сервер получает отдельный SSH-ключ и отдельный
каталог репозитория. Пароль Storage Box скрипт не сохраняет: он требуется
только SSH-клиенту для первоначальной установки публичного ключа.

До запуска мастера в Hetzner Console необходимо создать Storage Box, включить
**SSH Support** и **External Reachability**. Последний параметр обязателен для
серверов вне сети Hetzner. Неиспользуемые FTP, SMB и WebDAV включать не нужно.

#### Установка

Скрипт устанавливает пакеты из системного репозитория:

```bash
sudo apt-get install -y restic openssh-client
```

Сторонние репозитории не подключаются. Перед установкой показываются команды и
запрашивается подтверждение.

#### Защищённая конфигурация Storage Box

Мастер запрашивает:

- hostname и пользователя Storage Box;
- каталог для репозиториев;
- короткое имя текущего сервера;
- абсолютные пути, которые нужно копировать;
- отдельный пароль шифрования Restic длиной не менее 20 символов.

Конфигурация создаётся в каталоге:

```text
/etc/server-restic-backup
```

Каталог принадлежит `root:root` и имеет права `700`. Пароль репозитория,
приватный ключ, SSH-конфигурация, список источников и исключений имеют права
`600`. Приватный ключ создаётся без passphrase, потому что используется
автоматической systemd-службой, но доступен только `root`.

Пароль шифрования Restic необходимо отдельно сохранить в менеджере паролей.
Без него восстановить данные невозможно. Повторный запуск мастера не
перезаписывает существующий пароль и требует сначала вручную сохранить и
осознанно удалить прежнюю конфигурацию.

`ssh-keyscan` получает host key Storage Box, после чего скрипт показывает его
отпечаток. До установки публичного ключа пользователь должен сверить отпечаток
со сведениями Storage Box в Hetzner Console и ввести точное подтверждение `ПРОВЕРЕН`.
Это важно: слепое доверие результату `ssh-keyscan` не защищает первое
соединение от подмены сервера.

#### SSH-ключ и репозиторий

Отдельный пункт передаёт публичный ключ официальной команде Hetzner
`install-ssh-key` по порту `23`. Этот способ добавляет ключ в обоих форматах и
не удаляет уже установленные ключи. Пароль Storage Box вводится непосредственно
в SSH-клиенте и не попадает в аргументы команды, конфигурацию или журнал
скрипта.

После установки ключа следующий пункт:

1. проверяет SFTP-подключение в пакетном режиме;
2. определяет, существует ли конфигурация Restic;
3. выполняет `restic init` только для ещё не инициализированного репозитория.

Для каждого сервера используется путь вида:

```text
restic/<имя-сервера>
```

Это не позволяет смешивать независимые серверы в одном репозитории и упрощает
раздельное восстановление и удаление.

#### Автоматическое выполнение

Скрипт устанавливает root-owned файлы в `/usr/local/sbin` и четыре unit-файла
systemd. Файлы из каталога сайта или Git-репозитория от имени `root` не
исполняются.

Расписание по умолчанию:

- ежедневный backup — `03:30`, со случайной задержкой до 30 минут;
- проверка и очистка — по воскресеньям в `05:30`, также со случайной задержкой;
- пропущенный из-за выключенного сервера запуск выполняется после загрузки
  благодаря `Persistent=true`.

Одновременный запуск backup и обслуживания предотвращает `flock`. Ежедневный
процесс создаёт снимок и применяет политику хранения без физической очистки
пакетов. Еженедельный процесс сначала выполняет `restic check`, затем
`forget --prune`.

Политика хранения:

- 14 ежедневных снимков;
- 8 еженедельных;
- 12 ежемесячных.

Службы запускаются с пониженным CPU/I/O-приоритетом и ограничениями systemd.
Журнал доступен через `journalctl`.

После настройки рекомендуется включить независимые snapshots самого Storage
Box в Hetzner Console. Это дополнительная защита от удаления репозитория при
компрометации VPS и не заменяет снимки Restic.

#### Проверка и восстановление

Меню позволяет:

- запустить backup вручную;
- показать список снимков;
- выполнить полную проверку `restic check`;
- восстановить один выбранный абсолютный путь из последнего снимка в новый
  каталог `/root/restic-restore-tests/<дата-время>`.

Контрольное восстановление не записывает файлы поверх production. После ручной
проверки тестовый каталог удаляется вручную.

#### Важное ограничение баз данных

Restic копирует файлы. Он не гарантирует согласованную резервную копию живых
файлов MySQL, MariaDB или PostgreSQL. Каталоги данных СУБД нельзя просто
добавлять в список источников. Перед запуском Restic приложение должно создать
согласованный дамп своим отдельным root-owned скриптом, а каталог с дампом уже
можно включить в `sources`.

Механизм формирования дампа намеренно не универсализирован: параметры
MySQL/MariaDB, PostgreSQL, Docker и требования к блокировкам различаются между
серверами. После настройки Restic для каждого проекта нужно отдельно проверить,
что нужная база действительно попала в снимок и успешно восстанавливается.

## Что скрипт намеренно не делает

- не меняет SSH-порт;
- не запрещает вход `root` автоматически;
- не добавляет пользователя в `sudo` без отдельного действия и явного подтверждения;
- не устанавливает автоматически обычные функциональные обновления ОС, кроме security-репозитория;
- не настраивает общий фаервол для всех портов;
- не удаляет произвольные существующие правила `iptables`;
- не создаёт резервную копию всего VPS;
- не копирует живые файлы СУБД и не создаёт универсальный дамп базы данных;
- не подключает сторонний репозиторий Docker и не перезапускает работающий Docker автоматически;
- не заменяет проверку внешнего доступа с другого компьютера.

Эти действия зависят от архитектуры конкретного сервера и не должны выполняться универсальным скриптом без отдельного решения.

## Проверка после изменений

После применения настроек рекомендуется проверить:

```bash
sudo sshd -t
sudo sshd -T | grep -E 'passwordauthentication|pubkeyauthentication|kbdinteractiveauthentication'
sudo fail2ban-client -t
sudo fail2ban-client status
sudo nginx -t
sudo ss -lntup
sudo iptables -L -n -v --line-numbers
sudo ip6tables -L -n -v --line-numbers
sudo iptables-restore --test /etc/iptables/rules.v4
sudo ip6tables-restore --test /etc/iptables/rules.v6
docker --version
docker compose version
sudo systemctl status docker --no-pager
sudo systemctl status server-restic-backup.timer --no-pager
sudo systemctl status server-restic-maintenance.timer --no-pager
sudo journalctl -u server-restic-backup.service -n 100 --no-pager
```

Самая важная практическая проверка — вход по SSH-ключу и доступ к ISPmanager с разрешённого IP в отдельной сессии.
